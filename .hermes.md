# Project Project Instructions

These instructions apply to every Hermes agent working in this repository. They define shared project rules, environment requirements, artifact ownership, and coordination boundaries. The role specific skills under `.hermes/skills/` provide the detailed procedures for Lead, Engineer, Reviewer, and Pull Request delivery.

## 1. Project Context and Documentation

The project documentation under `.hermes/project/` is the primary source for intended requirements, architecture, workflows, technical constraints, and operational expectations.

All agents must:

1. Read the relevant documentation before making decisions or performing assigned work.
2. Discover documentation recursively under `.hermes/project/`, including nested directories.
3. Follow references to related documents when they contribute to understanding the requirements.
4. Consider requirements across documents rather than interpreting one file in isolation.
5. Use actual file paths and section headings when recording documentation references.
6. Identify conflicting, incomplete, inaccessible, or ambiguous documentation instead of inventing requirements.
7. Revisit relevant documentation when scope, requirements, architecture, or implementation changes.

Do not implement solely from a task description, conversation history, or plan summary.

### Source responsibilities

| Source | Responsibility |
|---|---|
| `.hermes/project/` | Intended requirements, architecture, workflows, technical specifications, and operational expectations |
| `README.md` | Usage documentation for the multi-agent workflow itself |
| `.hermes/memories/ROADMAP.md` | Full project roadmap and future milestone progression |
| `.hermes/memories/PLANS.md` | Approved scope for exactly one active milestone |
| `.hermes/memories/PROGRESS.md` | Complete implementation checklist and actual execution status |
| `.hermes/kanban/` (SQLite, `HERMES_KANBAN_BOARD`) | Live orchestration task state, assignments, handoffs, review requests, blockers |

Kanban database location: `$HERMES_KANBAN_HOME/kanban.db` (default board) or `$HERMES_KANBAN_HOME/kanban/boards/<slug>/kanban.db`, with `HERMES_KANBAN_HOME` set to `<PROJECT_ROOT>/.hermes` by the launcher.
| `.hermes/memories/reviews/` | Preserved independent review reports, managed by Lead |
| `.hermes/memories/archive/milestones/` | Archived plans for completed milestones, managed by Lead |
| Git history and repository | Evidence of actual implementation and changes |
| Tests and validation output | Evidence of observed behavior and verification |


Live task orchestration state is stored in the project Kanban board (SQLite), not in markdown files.
These sources have different responsibilities and must not silently override one another.

Approved user decisions and requirements govern authorized changes. Project documentation defines the intended system. `PLANS.md` defines the approved implementation scope. `PROGRESS.md` records execution status but does not prove correctness. Source code and Git history show what actually exists, not automatically what should exist.

If documentation, plan, progress, and implementation conflict, identify the discrepancy and follow the role specific escalation procedure. Do not silently choose an interpretation or change another agent's owned artifact.

## 2. Shared Project State

All shared project state is stored under `.hermes/memories/`.

### `.hermes/memories/PLANS.md`

This is the canonical active milestone plan.

- It is owned exclusively by Lead.
- It must contain exactly one active milestone, including that milestone's phases and planner TODO items.
- It is the approved scope Engineer must execute.
- Engineer and Reviewer may read it but must not modify it.
- Do not use it as a copy of the entire roadmap.

If the file is missing or empty, Lead must inspect `.hermes/memories/ROADMAP.md`, relevant project documentation, repository state, and progress history, then plan exactly one next eligible milestone. If the exact roadmap path is absent, Lead must locate and verify the actual canonical roadmap in `.hermes/project/` and record the discrepancy. Do not invent or rename roadmap files.

If the file contains an active milestone, Lead must preserve and validate it rather than regenerate it. Lead may replace or archive it only after the milestone completion conditions defined by the planner skill and workflow state have been verified.

### `.hermes/memories/PROGRESS.md`

This is the canonical implementation progress tracker.

- It is owned exclusively by Engineer.
- It must preserve the complete hierarchy: Milestone → Phase → Planner TODO Item → Implementation Subitem.
- It records implementation state, stable subitem identifiers, validation evidence, commit traceability, blockers, and relevant technical decisions.
- Lead and Reviewer may read it but must not modify it.
- Update the relevant checklist entries as work is performed. Do not append repetitive session summaries or replace the checklist with narrative status reports.

A checked item is not proof of correctness. Every completion claim must be verifiable against repository state, commits, and validation evidence.

- It records the current workflow state, active milestone and phase, active assignment, responsible next actor, candidate review commits, review round, finding status, approval state, PR state, and blockers.
- Engineer and Reviewer may read it but must not modify it.
- Lead must update it when ownership or workflow state changes.

Use the workflow state machine defined in the autonomous workflow instructions and planner skill. Do not infer that work is complete from conversational claims alone.

### Review reports and milestone archives

- Reviewer returns findings through its Herdr session and must not write into the repository.
- Lead preserves review reports under `.hermes/memories/reviews/`.
- Lead archives completed milestone plans under `.hermes/memories/archive/milestones/`.
- Do not edit or rewrite historical review reports to hide previous findings.

## 3. Agent Roles and Artifact Ownership

The autonomous workflow has three persistent agents and four skills.

| Agent | Profile role | Skill(s) | Owns |
|---|---|---|---|
| Lead | Planning and coordination | `planner` | `PLANS.md`, milestone archives, preserved review reports |
| Engineer | Implementation and delivery | `executor`, then `delivery` after review approval | Application code, tests, `PROGRESS.md`, implementation commits, approved PR creation |
| Reviewer | Independent review | `reviewer` | Independent assessment returned to Lead; no repository artifact ownership |

`delivery` is Engineer's PR skill, not a fourth agent.

### Ownership restrictions

**Lead**
- May read all project files and inspect implementation and Git state.
- May create and maintain the active milestone plan and workflow state.
- Must not modify application source code, tests, or `PROGRESS.md`.
- Must not commit, stage, reset, rebase, or push Engineer's implementation while Engineer is active.

**Engineer**
- May modify application code, tests, implementation documentation, and `PROGRESS.md` as required by approved scope.
- Must execute the approved scope in `PLANS.md` and follow relevant `.hermes/project/` guidance.
- Must not replace or independently regenerate `PLANS.md`.
- Must not modify review reports.
- Must stop at the phase review gate and must not create a PR before actual independent approval.
- May create the PR only after Lead verifies approval for the exact candidate commit and authorizes delivery.
- Must not approve or merge PRs.

**Reviewer**
- Must independently inspect documentation, plans, progress, Git changes, implementation, tests, and validation evidence.
- Must not modify any project file, source code, tests, configuration, documentation, plan, progress tracker, workflow state, or Git history.
- Must not fix findings.
- Must return a structured report to Lead through Herdr.

No agent may silently modify another agent's authoritative artifact.

## 4. One Active Milestone at a Time

The full project roadmap remains in `.hermes/memories/ROADMAP.md`.

`PLANS.md` is an active milestone slot, not a full-project plan.

Lead must:

1. Read `PLANS.md` and `PROGRESS.md` before deciding the next action.
2. If `PLANS.md` is missing or empty, inspect the roadmap, relevant .hermes/project, repository state, and completed milestone history.
3. Select the next eligible milestone according to documented dependencies and approval gates.
4. Create a plan for that milestone only.
5. Include its phases, planner TODO items, documentation references, dependencies, validation requirements, and acceptance criteria.
6. Avoid planning detailed implementation for later milestones.
7. If `PLANS.md` already contains an active milestone, preserve it and direct Engineer to the next eligible work item.

Do not clear or archive an active milestone because its implementation phase is complete. Milestone closure requires all required phases to pass independent review, required PRs to be merged or otherwise integrated as explicitly authorized, dependencies to be verified, and milestone exit criteria to be satisfied.

## 5. Documentation-Driven Implementation and Engineering Quality

All agents must respect these project-wide engineering principles. Their role specific skills define how to apply them.

1. Documented requirements and architecture take precedence over personal preference.
2. Preserve one authoritative owner per concern, including data, business rules, schemas, configuration, contracts, permissions, and state transitions.
3. Distinguish canonical data from legitimate derived, cached, replicated, or generated representations.
4. Do not introduce competing sources of truth or uncontrolled multiple writers.
5. Inspect existing project functionality before creating new functionality.
6. Consider existing framework capabilities and installed libraries before custom implementation.
7. Justify new dependencies and custom implementations with evidence.
8. Avoid unnecessary boilerplate, abstractions, wrappers, duplicate services, and parallel implementations.
9. Preserve existing module responsibilities, interfaces, and integration contracts unless an approved requirement requires a change.
10. Do not silently expand scope or implement future milestone work prematurely.
11. Do not treat passing tests as sufficient proof of architectural correctness.
12. Do not present assumptions, recommendations, or unverified results as facts.

## 6. Lead and Engineer Coordination

Lead and Engineer may work concurrently, but shared artifact ownership must remain exclusive.

- Lead supervises scope, documentation alignment, dependencies, and completed implementation boundaries.
- Engineer performs implementation, testing, commits, and progress updates.
- Lead should inspect stable completed subitems and commits rather than treating an actively edited working tree as a completed result.
- Engineer reports each completed subitem to Lead with its stable ID, documentation references, implementation summary, validation, commit, working-tree state, blockers, and next eligible task.
- Lead compares completed work against the approved plan and documentation and provides focused feedback through Herdr.
- Engineer must pause affected work when a requirement conflict, material architecture decision, ownership ambiguity, or scope change requires Lead or user decision.
- A plan change must be authorized and recorded by Lead before Engineer executes the changed scope.

Do not assign overlapping implementation work to Engineer while an existing assignment is still active unless the new message is a deliberate clarification, correction, or stop instruction.

## 7. Independent Review and Phase Freeze

At the end of a phase, Engineer must stop implementation and prepare a committed candidate for independent review.

Live orchestration state (review rounds, candidate commits, etc.) is tracked in the Kanban board.

Reviewer must inspect that exact candidate range and the relevant documentation, plan, progress, implementation, and validation evidence.

Engineer must not modify the candidate while it is under review. If a material change is required, Lead must establish a new candidate commit and request review of the updated range.

Lead triages findings. Engineer fixes valid findings and provides corrective commit and validation evidence. Reviewer independently verifies corrections. Repeat until all required findings are closed, rejected with evidence, or explicitly accepted as risks by the authorized owner.

A review approval applies only to the exact candidate commit reviewed. It does not automatically approve subsequent changes.

## 8. Pull Request and Merge Boundaries

Engineer may load the `delivery` skill and create a PR only after:

1. Reviewer has explicitly approved the exact candidate commit.
2. Lead has verified that the current branch head still matches the approved candidate or that all intervening changes have been reviewed.
3. No required review findings remain unresolved.
4. Required implementation and validation gates are satisfied.
5. Lead has authorized the delivery handoff.

The PR must target `master` unless an explicitly approved project workflow specifies otherwise.

Engineer must inspect the complete branch diff, read relevant documentation and plan/progress context, write an accurate description, create the PR, and verify its URL and status.

No agent may approve or merge the PR unless the user explicitly authorizes a separate merge workflow. A dependent next milestone must not begin until required integration and dependency state are verified.

## 9. Git and Working-Tree Safety

The repository working tree is shared during normal Lead and Engineer operation. Respect exclusive artifact ownership.

Engineer owns implementation branch changes, staging, commits, and authorized pushes.

Lead may inspect Git state but must not change Engineer's branch or working tree while Engineer is active.

Engineer must:

1. Inspect `git status` before changing files.
2. Understand existing staged, unstaged, and untracked changes.
3. Stage explicit file paths only.
4. Never use `git add .` or `git add -A` for implementation subitem commits.
5. Keep each implementation subitem's changes isolated.
6. Avoid accidentally staging Lead-owned plan or workflow files and review reports.
7. Never discard or reset changes without understanding their origin and obtaining required authorization.
8. Never rewrite shared Git history without establishing that it is safe.

Reviewer should use an isolated review worktree or read-only checkout whenever available. A separate Hermes profile is not a filesystem sandbox. Do not assume role instructions alone prevent filesystem modifications.

## 10. Environment Requirements

Before running any `node`, `npm`, `pnpm`, or `yarn` commands in the terminal, ensure the Node version specified in `.nvmrc` is active.

For NVM, use:

```bash
export NVM_DIR="$HOME/.nvm" && [ -s "$NVM_DIR/nvm.sh" ] && . "$NVM_DIR/nvm.sh" && nvm use
```

For fnm, use the shell initialization appropriate to the current shell, then:

```bash
eval "$(fnm env)" && fnm use
```

Verify the active version against `.nvmrc` before executing project Node commands:

```bash
node --version
cat .nvmrc
```

If the required Node version manager is unavailable or the configured version cannot be activated, report the environment blocker. Do not silently use a different Node version.

## 11. Session Initialization and Handoff

At session start, every agent must read this `.hermes.md` file and its complete assigned skill before performing role specific work.

Then read the shared state relevant to its role:

- Lead: `PLANS.md`, `PROGRESS.md`, `.hermes/memories/ROADMAP.md`, and relevant `.hermes/project/`.
- Engineer: `PLANS.md`, `PROGRESS.md`, and all relevant `.hermes/project/`.
- Reviewer: `PLANS.md`, `PROGRESS.md`, relevant `.hermes/project/`, exact review scope, Git history, and candidate diff.

Reconstruct state from repository files and Git evidence. Do not depend on conversation history or profile memory as the sole record of project state.

At handoff or session end:

- Lead records orchestration state in the Kanban board.
- Engineer updates the relevant entries in `PROGRESS.md` and reports commits, validation, blockers, and next work to Lead.
- Reviewer returns findings and review outcome to Lead without modifying repository files.

Do not append repetitive summaries to memory files. Update the authoritative section or record only the information needed to resume work accurately.

## 12. Final Operating Rules

1. Documentation before assumptions.
2. Approved plan before implementation.
3. One active milestone in `PLANS.md`.
4. One owner per shared artifact.
5. One authoritative owner per domain concern.
6. Reuse before recreation.
7. Evidence before completion claims.
8. Independent review before PR creation.
9. Exact candidate commit before review approval.
10. No unauthorized scope changes, file modifications, PR approvals, or merges.

These shared instructions apply to all Project agents. The relevant skill defines the detailed procedure for each role and must remain consistent with this file.
