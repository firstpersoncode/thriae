# Project Project Instructions

These instructions apply to every Hermes agent working in this repository. They define shared project rules, environment requirements, and coordination boundaries. The Lead agent uses the `planner` skill as its primary operating procedure. All other skills are defined under `.hermes/skills/` and are not explained here.

## 1. Project Context and Documentation

The project documentation under `.hermes/project/` is the primary source for intended requirements, architecture, workflows, technical constraints, and operational expectations.

All agents must:

1. Read the relevant documentation before making decisions or performing assigned work.
2. Discover documentation recursively under `.hermes/project/`, including nested directories.
3. Follow references to related documents when they contribute to understanding the requirements.
4. Consider requirements across documents rather than interpreting one file in isolation.
5. Use actual file paths and section headings when recording documentation references.
6. Identify conflicting, incomplete, inaccessible, or ambiguous documentation instead of inventing requirements.
7. Revisit relevant documentation when scope, requirements, architecture, or implementation changes.

Do not implement solely from a task description, conversation history, or plan summary.

### Source responsibilities

| Source | Responsibility |
|---|---|
| `.hermes/project/` | Intended requirements, architecture, workflows, technical specifications, and operational expectations |
| `README.md` | Usage documentation for the multi-agent workflow itself |
| `.hermes/memories/ROADMAP.md` | Full project roadmap and future milestone progression |
| `.hermes/memories/PLANS.md` | Approved scope for exactly one active milestone |
| `.hermes/kanban/` (SQLite, `HERMES_KANBAN_BOARD`) | Live orchestration task state, assignments, handoffs, review requests, blockers |
| `.hermes/memories/reviews/` | Preserved independent review reports |
| `.hermes/memories/archive/milestones/` | Archived plans for completed milestones |
| Git history and repository | Evidence of actual implementation and changes |
| Tests and validation output | Evidence of observed behavior and verification |

Live task orchestration state is stored in the project Kanban board (SQLite), not in markdown files.

Approved user decisions and requirements govern authorized changes. Project documentation defines the intended system. `PLANS.md` defines the approved implementation scope. Source code and Git history show what actually exists, not automatically what should exist.

## 3. Agent Roles and Artifact Ownership

Agents are defined by the profile folders under `.hermes/profiles/`. Each profile loads the skills listed in its `skills.txt` and uses its `initial_prompt.txt` at startup.

No predefined skills, profiles, or agent counts are assumed. Any profile may be added under `.hermes/profiles/` with any combination of skills.

The Lead agent is required and uses the `planner` skill as its primary operating procedure. Lead orchestrates other agents via Kanban and Herdr.

### Ownership restrictions

**Planning agent (Lead)**

- May read all project files and inspect implementation and Git state.
- May create and maintain the active milestone plan.
- Must not modify application source code or tests.

No agent may silently modify another agent's authoritative artifact.

## 4. Environment Requirements

Before running any `node`, `npm`, `pnpm`, or `yarn` commands in the terminal, ensure the Node version specified in `.nvmrc` is active.

For NVM, use:

```bash
export NVM_DIR="$HOME/.nvm" && [ -s "$NVM_DIR/nvm.sh" ] && . "$NVM_DIR/nvm.sh" && nvm use
```

For fnm, use the shell initialization appropriate to the current shell, then:

```bash
eval "$(fnm env)" && fnm use
```

Verify the active version against `.nvmrc` before executing project Node commands:

```bash
node --version
cat .nvmrc
```

If the required Node version manager is unavailable or the configured version cannot be activated, report the environment blocker. Do not silently use a different Node version.

### Kanban environment (mandatory before any Kanban operation)

Kanban state for this project must live under `<PROJECT_ROOT>/.hermes`, never under the user home directory. Before any `kanban_*` tool call or `hermes kanban` CLI command, verify the agent/runtime environment:

```bash
echo "HERMES_KANBAN_HOME=${HERMES_KANBAN_HOME:-<unset>}"
echo "HERMES_KANBAN_BOARD=${HERMES_KANBAN_BOARD:-<unset>}"
```

`HERMES_KANBAN_HOME` must equal `<PROJECT_ROOT>/.hermes` (the project root is the directory containing this `.hermes.md`). `HERMES_KANBAN_BOARD` must equal the project board slug (derived from the project directory name).

If either is unset or points elsewhere:

1. Do NOT create, modify, or seed Kanban tasks. Creating tasks with an unset/mispointed `HERMES_KANBAN_HOME` silently writes them to `~/.hermes` (or another project's board), which corrupts cross-project state.
2. Escalate as an environment blocker instead of proceeding.
3. Prefer launching agents through the project's `Start-Agents.sh`, which exports both variables correctly. Manual agent launches must export them explicitly:

```bash
export HERMES_KANBAN_HOME="$(git rev-parse --show-toplevel)/.hermes"
export HERMES_KANBAN_BOARD="$(basename "$(git rev-parse --show-toplevel)" | tr '[:upper:]' '[:lower:]' | sed 's/[^a-z0-9]/-/g; s/-\+/-/g; s/^-//; s/-$//')"
```

When `HERMES_KANBAN_HOME` cannot be corrected, use the explicit database path for inspection only (`HERMES_KANBAN_DB=<PROJECT_ROOT>/.hermes/kanban/boards/<slug>/kanban.db`) and do not create tasks.

Do not manually edit agent profile `.env` files to set Kanban (or any other) environment variables. Profile `.env` files are overwritten in full by `Start-Agents.sh`'s credential distribution step, so hand edits silently disappear and can drift between profiles. Persist environment variables through `Start-Agents.sh` (which writes them idempotently) so there is one owner and one source of truth. If a value must change outside a launcher run, escalate to the user rather than editing the profile by hand.

## 5. Git and Working-Tree Safety

The repository working tree is shared during normal agent operation. Respect exclusive artifact ownership.

Agents must:

1. Inspect `git status` before changing files.
2. Understand existing staged, unstaged, and untracked changes.
3. Stage explicit file paths only.
4. Never use `git add .` or `git add -A` for implementation subitem commits.
5. Keep each implementation subitem's changes isolated.
6. Avoid accidentally staging Lead-owned plan files and review reports.
7. Never discard or reset changes without understanding their origin and obtaining required authorization.
8. Never rewrite shared Git history without establishing that it is safe.

A separate Hermes profile is not a filesystem sandbox. Do not assume role instructions alone prevent filesystem modifications.

## 7. Final Operating Rules

1. Documentation before assumptions.
2. Approved plan before implementation.
3. One active milestone in `PLANS.md`.
4. One owner per shared artifact.
5. One authoritative owner per domain concern.
6. Reuse before recreation.
7. Evidence before completion claims.
8. Independent review before PR creation.
9. Exact candidate commit before review approval.
10. No unauthorized scope changes, file modifications, PR approvals, or merges.

These shared instructions apply to all Project agents. The relevant skill defines the detailed procedure for each role and must remain consistent with this file.
